Pyodide Worker
===================
To get a more fluid rendering in the frontend, pyodide is moved to a webworker.
In this worker, all functions for simplipfy are called.

Classes
---------
- WorkerCommunication
    - creates the worker it communicates with
    - defines how messages are send and received to and from the worker
    - handles request timeouts
    - tracks active requests to its worker

- APIBase
    - defines the base class for all API classes that communicate with the worker
    - wraps the WorkerCommunication functions requestResponse and getDataPromise
    - constructor defines what a API class needs to work

- WorkerRequest
    - defines a request to the worker
    - id of the request
    - data for the request
    - timeout time for the request

- WorkerResponse
    - defines a response from the worker
    - id of the request, this response belongs to
    - if the request was successful
    - the data returned by the worker
    - warnings generated by the worker during the execution of the request
    - errors that occurred during the execution of the request

- ActiveRequest
    - wraps a WorkerRequest while the WorkerCommunication class waits for a response from the worker
    - tracks the timeout for the request
    - holds the resolve function for the promise returned to the frontend


Implementation
---------------

Overview
~~~~~~~~~

Frontend
~~~~~~~~~

The WorkerCommunication class creates its worker from a given js file. It then appends an event listener to the worker
that is triggered on a message event. The behavior of the event listener is defined in onMessageEvent.
onMessageEvent checks for each message of the worker if the received message id is in the active requests
of the WorkerCommunication class. If it is, the promise is resolved and the active request is removed from the map
of active requests. If it is not, the message is ignored because it can´t be processed. Each request has a timeout,
that is specified in the WorkerRequest class. If a request times out it does not throw an error it resolves to a
WorkerResponse that is unsuccessful. The WorkerResponse then has an error message and is of the class TimeOutResponse.

Worker
~~~~~~~
The worker sets up a onMessageEvent listener each message it receives is expected to be a WorkerRequest.
The message it receives can`t actually have the class WorkerRequest but has to have the same properties. Each for
the request the action is used to find the right function in the handlers defined in pyodideWorker.js.
The function then is executed with the data provided in the request. When the function finishes the result is sent back
via postMessage. The the result has to have the same properties as a WorkerResponse. If the function throws errors or
generates warnings during the execution, these are caught and sent back in the errors and warnings fields.

Usage
--------

Extending an API
~~~~~~~~~~~~~~~~~

To Extend an API, you need to edit these files:
    - in ``...Pyodide/src/scripts/pyodideAPI/<APIName>API.js`` ::

            <APIName> extend <APIBase | SolverInterface> {
                newFunction(data) {
                    return this.getDataPromise("newFunction", data);
                }

            }

    - in ``...Pyodide/src/scripts/pyodideWorker.js`` ::

            const handlers = {

            // ================= <APIName>API =================
            /** @returns {Promise<HandlerResponse<newFunction>>} */
            newFunction: async (data) => {
                let result = await self.pyodide.newFunction(data);
                // optionally catch errors or generate warnings, default values are [] for both
                errors = [...];
                warnings = [...];
                return new HandlerResponse(result, errors, warnings);
            },

    The pyodideWorker holds references to Solvers in the backend, you need to know where to find your function or object
    and make the according call. The worker holds these references:

        - self.pyodide -> pyodide functionality itself like file system calls
        - self.solveModule -> an import of the file ``...inskale/Pyodide/simplipfyAPI.py`` to simplify solver object access
        - self.stepSolve -> the module used for solving stepwise in the frontend
        - self.kirchhoffSolver -> the module used for solving kirchhoff in the frontend
        - self.magneticTransformer -> the module used for solving magnetic in the frontend
        - self.svgGenerator -> the module used for generating circuit svgs in the frontend
        - self.drawingConfig -> the module used to configure how svgs are drawn for the frontend

    You can add references if you need new ones, look at the StepSolveAPI as a good example.

    - in ``...Pyodide/src/scripts/pyodideAPI/workerCommunication.js``, extend the PyodideAPI JSDoc string ::

        /**
        * @typedef {Object} PyodideAPIMap
        * ...
        * // ================= <APIName> API =================
        * @property {{input: {<paramName1>: <type>, <paramName2>: <type>...}, output: <type>}} newFunction

    This is used for type inference to get autocompletion and type hints in the frontend and the correct return
    types of the backend function calls.

Creating a new API
~~~~~~~~~~~~~~~~~~~

To create a new API you need to create ``...Pyodide/src/scripts/pyodideAPI/<APIName>API.js``. If you extend
APIBase or SolverInterface depends on where the api is used. If the api is used to solve circuits on the learn Page
it needs to implement the SolverInterface else it can extend the APIBase class.
Add a new section with the API name to the handlers in ``...Pyodide/src/scripts/pyodideWorker.js`` and add a new section
with the API name to ``...Pyodide/src/scripts/pyodideAPI/workerCommunication.js``. You need to declare each function
you want to use in each of those files.
